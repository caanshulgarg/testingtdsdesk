What is new in 2.1.6 (over the 2.1.4 build that was never handed out, and over the held-back 2.1.5)
  - Tally's per-ledger voucher list ("Vouchers : Ledger") is never asked: Tally builds that list ledger by ledger, the
    same shape of read that hung Tally on 02-Oct-2026 (ledgers 696-699).
  - After a posting, and when a posting is resumed or retried, the entries are looked for by their FinCom id alone
    (FinComTag: one date's entries, heads and narration only, one request per date).
  - FinCom's "a ledger's entries" (/ledgervouchers, /ledgerlines) is answered from the copy kept on this computer; for
    a period the copy does not cover it says the entries are shown from FinCom's copy. Tally is not asked.
  - No request may hold Tally longer than 20 s (was 25 s). No request asks for more than one month of entries or more
    than 2,000 ledgers (FinCom's ledger lists are read 2,000 MasterIDs a request too).
  - Only the requests on the allow-list (docs/tally-allowlist.md) are sent to Tally; any other is refused before
    anything is sent, with a "refused: The request ... is not on the bridge's allow-list" line in the log.
  - A ledger that hangs Tally: the ledger-list chunk holding it is halved down to its one MasterID; that ledger is then
    skipped in every later read, named in the log ("the ledger with MasterID N (name) does not answer and holds Tally;
    it is skipped from now on and named to FinCom") and sent to FinCom with the ledger list; the rest of the list arrives.

What is new in 2.1.4 (since 2.1.3)
  - Tally is never asked for a balance: no opening balances read a batch at a time (TDSDeskKeepBal), no trial balance,
    no ledger balance, no Ledger Vouchers report. FinCom works balances out from its copy of the books.
  - Until the change read is measured, Tally is read only by Update now and the nightly run: the day book of the year,
    a month a request (a month that does not answer in 20 s is read again in halves, down to a day), each month saved as
    it comes. Opening a client in FinCom, or a posting, reads nothing from Tally.
  - The plain ledger and group lists come back (02-Oct-2026): Update now (and the nightly run) also reads every
    ledger's name, group, stored opening (the master's own field, not a balance), GSTIN, PAN, GUID, MasterID and AlterID,
    2,000 ledgers a request by MasterID (a chunk that does not answer in 20 s is read again in halves, from where it
    stopped), and the groups in one request. The list is also read once after a posting that made a new ledger, and when
    FinCom's ledger chooser asks for it (at most once per company every 3 minutes). A ledger renamed in Tally is renamed
    in FinCom (the old name kept); one deleted in Tally is marked deleted in FinCom, never removed.
  - One request to Tally at a time; a posting goes before anything else waiting. After a request Tally did not answer,
    nothing is sent except one small check (the company's name and GUID), at most once a minute, until Tally answers it.
  - The company's GUID is held: a company of the same name with another GUID (restored, re-created) is neither read nor
    posted to.
  - (03-Oct rebuild, after job 3b03cc5e was sent twice on NWS144) Every FinCom id Tally accepted or that was confirmed in
    Tally is written to sync\posted-ids.json on the Tally computer; an entry whose id is there is never sent again by any
    route (the cloud handing the job back, Post again, Retry, a restart): it is only looked for, first by the voucher id
    Tally gave (LASTVCHID, request FinComByMaster), then by its tag on its date, and shows "unknown (accepted)" until
    found. Before any send Tally is still asked for the id (the "Already in Tally" check). An owner's release in FinCom
    ("Not in Tally — release", with a reason) that the cloud hands over with the job lets the entry go once more, once
    per release (the cloud alone judges whether a release is in force; the bridge remembers the releases it honoured);
    the log says "entry <id>: released by <who> at <when> (<why>); sent once more". An entry held after a batch Tally
    made only partly is on disk too: no later job sends it ("Tally may have made this entry in a batch on <date> (job X)"). An entry of a batch Tally made only partly is
    held (unknown), never sent again one by one. The measure routes write the report under the bridge's folder only.
  - (03-Oct, gap 2) A failed read is told apart from an empty day. Each day the bridge sends carries n (the vouchers
    read) and empty:true only when all three hold: (1) Tally's answer for that day came in full, a whole envelope
    opened and closed, with no error line, every voucher in it decoded (no timeout, no silence, no connection dropped
    half-way, no decoder stop) and the self-watch did not stop reading during it; (2) the company's GUID was the one
    held (a company of the same name with another GUID is not read at all); (3) the answer listed no voucher for that
    day. A read that failed in any way keeps nothing: no day of it goes to FinCom (it is read again, the slice halved
    down to a day), so FinCom never sees it as empty. Only an empty day the bridge read in full (empty:true) makes
    FinCom mark that day's entries deleted; a day without the flag is a short read and marks nothing.
  - (03-Oct, owner-approved) PostOnly: the settings may name the companies this computer posts to ("PostOnly": ["ZZ
    TEST"]); the pilot installer sets it to ZZ TEST. A posting aimed at any other company is refused before one request
    goes to Tally, every entry failed with "This computer posts only to ZZ TEST (PostOnly); posting to <company>
    refused"; the heartbeat carries the list (postOnly). PostOnly covers every path: the posting queue, the local
    /import route (any program on this computer with the bridge key) and /unpost ("... removing from <company> refused"). The full-answer rule: a day counts as read only when Tally's
    answer came in full (see the gap-2 item above); only an empty day read in full is sent as empty.
  - The ledger list sent to FinCom carries each ledger's state (LEDSTATENAME) as its 10th column.
  - Every voucher posted carries its FinCom id in its narration ("TDSDesk:<id>"; since 2.1.6 it
    is written FIRST, "TDSDesk:<id> | <narration>", so a narration cut short can never lose it, and it is found wherever
    it stands); before posting, Tally is looked through for that id on the voucher's date first, then the party / bill /
    date / amount check of 2.1.4.
  - A posting sent when Tally stopped answering shows "Checking whether it reached Tally" and is not sent again until
    Tally answers and the id has been looked for: found -> In Tally; not found -> sent once more.
  - Only one bridge reads or posts a company at a time (a lease in FinCom's cloud, once migration-32 is applied).
  - Measure Tally (for FinCom support), in the tray and as a command: see docs/tally-measure-sheet.txt.
