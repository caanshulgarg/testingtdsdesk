## Checked, no finding

- **FinComEmployees request.** It is a CostCentre `fcCollection` with exactly the twelve approved fields, no period, ranges of 2,000 MasterIDs up to the master counter and then the open end, and the `pinned.go` rebuild refuses a range over 2,000. The `requestClass` is "undated". The answer is filtered in `empRowsOf` before anything is logged, stored or sent (a non-payroll row is only counted). It is read only when the counter has moved, with a 30-minute gap, not during a posting, not while the retry schedule is pending, through `invokeTally` (one in flight) with `recorderTC`'s 2 s hard stop, and only from the bridge's own port (`ledOwnPort`). The whole list is sent only when its hash changes, and the cloud marks employees missing from it gone, never deleting them.
- **The four ledger fields.** They are added after 2.4.3's fields in `ledFetch` (shared by the three requests), "Not Applicable" is sent blank, and the held, read and outbox files carry the columns at 13-16. A 2.4.3 outbox row is sent without them, and the cloud leaves its own values (`ledPay` returns null below 18 columns).
- **The kept list.** `BANKEMPLOYEENAME` and `AMOUNT` are kept only in an allocation whose `BANKEMPLOYEENAME` is filled. `ACCOUNTNUMBER`, `IFSCODE` and `PAYMENTFAVOURING` are refused by `fastPathOK` whatever list approves them. Other entries strip as in 2.4.3. The request bytes are unchanged (ce0e72f74e72).
- **The 3 s exception.** `entryTC` raises only a background, non-person TC that is exactly at the recorder limit, to at most 3,000 ms, and only for FinComVoucherObject on a single-entry ask. `slowNote` treats as in time only an answer within that raised limit. Every other request is unchanged.
- **Allow-list.** It has the five rows, the decision line for 2.4.4 and the new table hash. The pin and allow tests pass.
- **Migration 74.** It is add-only (`add column if not exists`, `create … if not exists`, no delete). RLS on `tally_employees` and `tally_salary_pays` is the same `firm_id = public.my_firm()` select policy as 57 and 73, with select for authenticated and all for service_role. `tally_ingest_salpay` is granted to nobody, and `tally_ingest_employees` to service_role only. The new `tally_ingest_details` is 73's text byte for byte, plus the one line marked "74".
- **index.ts.** It has the `employees` kind behind `bookFor` and the ledger-list rate limit, columns 15-18 only when present, and a fallback when 74's columns are absent. parse.js reads no account, IFSC or name in favour. The app reads salary payments only for the entry's live AlterID, so rows of an earlier version do not count.
- **Tax rules checked as correct.** The new-regime slabs, the 87A rebate to ₹12 L with marginal relief, the old-regime slabs and ₹12,500 rebate, standard deduction ₹75,000 / ₹50,000, surcharge rates (new regime capped at 25%) with marginal relief at each threshold, 4% cess, and 288A / 288B rounding (the same as ignoring paise and then rounding on the last digit).
- **FinCom-entered details.** They are kept per employee as `payDetails` items keyed by Tally GUID, and nothing from Tally overwrites them. The no-PAN check in "before filing" and the challan auto-tag tag only untagged rows, never one a person tagged.
- **Other rules.** No AI, no date of birth or Aadhaar field anywhere, and senior citizen is asked as yes / no for the old regime only.

Verdict: 3 High, 3 Medium, 3 Low.
