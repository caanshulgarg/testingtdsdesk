## Checked, no new finding

Financial accuracy, path by path (P = my probe, at cdd21a2):

- **Blocked 17(5) credit and reverse charge are never carried over a value Tally gave for the current version.** On the own path (P1), only nature and supply are carried. On the stale-newer path (P5: stale at 3 says false/false, Day Book at 2 says true/true), the result is false/false, because the held version gives only nature and supply. On the stale-older path, the held version is the newer one and wins: P7 (Day Book at 5 RCM true, stale at 3 false) gives true, and P8 (stale at 3 blocked and RCM, Day Book at 5 neither) gives false/false. P15 (an own read at 9 says false/false over a blocked/RCM Day Book, then a version at 12 comes without a type) stays false/false. d4f2d95 gave true/true there, because the round-3 bug also leaked into the stored entry.
- **Inferred blocked credit:** `ineligibleFlag` and `rcm` come only from Tally's tags or a held or stale version's tags. `fill` copies only truthy values (`:107`), so a carry never turns a mark on from nothing. A mark can be carried only from the newer of the two older versions.
- **SEZ and export with or without payment:** `nature` is read only by `supplyClass` (`04-…js:377`, the /SEZ/ test). Export is decided by `country` and the voucher type (`:375`). Because the own path no longer carries `country`, an own read with a blank country is never made an export from an older one (P1b). P9 is an own item read whose party is now "Regular", over a Day Book whose nature says SEZ. It still carries the SEZ nature. That is the nature-only carry round 3 asked for, d4f2d95 did the same, and an SEZ party is often "Regular" in Tally, so this is not a regression and I do not raise it. On 3.0–6.2 the Day Book reads the same blank item tags, so it seldom has a nature to carry.
- **Nil, exempt and non-GST:** `taxability` is never carried onto an own type (P1, P2). On the stale paths it comes from the newer of the two older versions, never from a mixed one (its taxability is blanked at `:87` before `gstStale` is made).
- **Goods/services:** `supply` follows the same blank-only carry as `nature`. That matters for 3B 3.1(d) and 4(A)(1)/(2) imports (`12-…js:246-250`). Tally gives it from the same tag in both the Day Book and the bridge, so a blank in one is normally a blank in the other.
- **Unchanged paths:** P11 (no type, Day Book held) carries the full `CARRY` list, as before 2.4.2. P12 (own type, nothing held) carries nothing. P13 (stale type, nothing held) carries the stale type and marks it `carried`. P10 (own type with a nature) keeps Tally's nature over the Day Book's. The `wins()` guard is unchanged, so an entry with an unknown held AlterID never reaches `fill`. `staleNewer` lost the `have.alt == null` arm, which round 3 found unreachable for the same reason.
- **`carried`:** it is built by concatenation over disjoint keys (the second `fill` filters `!v[x]`), so there are no duplicates. It is still not rendered anywhere (`58-ledgers.js:252` `e.carried` is a different, ledger-level object).
- **XSS / DoS / SQL / Tally request:** no new rendered value. `gstOwn` is a boolean, and `gstStale` is still deleted before storing (`:117`). `fill` is O(keys). There are no parse.js, bridge-go or migration changes in the range, and next-gsttype's only new commit is docs.
