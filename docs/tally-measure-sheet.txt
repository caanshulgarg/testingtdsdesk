MEASURING TALLY FOR FINCOM (FinCom Bridge 2.1.4) - STEP BY STEP

Why: nobody can measure Tally from FinCom's side. Before FinCom reads only what changed in Tally (by Tally's change
number, the AlterID), the owner wants measured numbers: how long each kind of request takes on a real Tally, how big it
is, which ledger hangs Tally, and what moves the AlterID. The bridge does the measuring itself, one request at a time,
each stopped after 20 s, and nothing is written to Tally. A run stops at the FIRST request that does not answer in 20 s:
nothing more is sent but the small company check (waited for, up to 10 minutes), and the run ends with that in the
report. The tool is started by a person only: the tray item, or the measure command typed in a Command Prompt (both go
through the running bridge, whatever its run mode); the bridge never starts one by itself, no web page (FinCom's own
included) can start it, and the command never measures beside a running bridge (a busy bridge: "Not measured", try later).

Where the numbers go: a plain text report in the bridge's folder (for "Just for me" installs:
%LOCALAPPDATA%\FinCom Bridge), named measure-<company>-<date-time>.txt. Snapshots are measure-snap-<label>.json there.

Commands (in a Command Prompt, in the bridge's folder; "FinComBridge.exe" is the installed program):
   FinComBridge.exe measure --company "ZZ TEST"                          (items a to e and f0; no single ledger)
   FinComBridge.exe measure --company "ZZ TEST" --ledgers 696             (ONE ledger: part A3, after working hours only)
   FinComBridge.exe measure --company "ZZ TEST" --snapshot before [--month 202610]
   FinComBridge.exe measure --compare before after
The running bridge does the requests (through its queue: a posting still goes first). From the tray: right-click the
icon > Measure Tally (for FinCom support) measures the company open in Tally and opens the report when it is done.


PART A. THE REPORT (items a to f)

A1. ON GARG SHEKHAR & COMPANY (NWS144) AND ON ZZ TEST
   Do: TallyPrime open with the company, nobody else working in it. Close FinCom on other computers for these minutes.
       Right-click the bridge icon > Measure Tally (for FinCom support). Wait (a few minutes; up to 10 if a ledger hangs).
   You should see: the report opens. Its lines:
       a   the company check: the company's GUID and highest AlterIDs
       b   about 500 entries (AlterID above highest - 500) over the whole year, every field FinCom needs
       c1  the same, this month only;  c2  the same, the busiest month only (c0: the year's dates, to find it)
       d   the GUID list only, this month
       e   one entry with every field: its size, and for each field "present", "present, empty" or "absent"
       f0  every ledger's name (the count); the line "f696.." says the single ledgers are not run by default: they
           are part A3, after working hours only.
   Write down: the ms, bytes and count of every line.
   If not: send the report file and icon > Show log.

A3. THE LEDGERS 696-699 - AFTER WORKING HOURS ONLY, OPTIONAL, ONE LEDGER AT A TIME
   These four ledgers (numbered 696-699 in name order) are the ones that hung Tally on 02-Oct-2026. Do this part only
   after working hours, with nobody working in Tally on any computer, and only if you want to. Never during the day.
   One ledger per run; close and reopen TallyPrime between runs if you like (allowed, not required):
       FinComBridge.exe measure --company "GARG SHEKHAR & COMPANY" --ledgers 696
       (wait for the report; then, when you are ready)
       FinComBridge.exe measure --company "GARG SHEKHAR & COMPANY" --ledgers 697
       FinComBridge.exe measure --company "GARG SHEKHAR & COMPANY" --ledgers 698
       FinComBridge.exe measure --company "GARG SHEKHAR & COMPANY" --ledgers 699
   You should see, per run: f<N>-check (the company check), f<N>-fields (that ledger's master fields: parent, is
       revenue, affects stock, bill-wise, cost centres), f<N>-opening (the opening its master stores). A request that
       does not answer in 20 s says HANGS; the run stops at that first request: the bridge then sends nothing but the
       small company check until Tally answers it (it waits up to 10 minutes), and the report ends with "waiting for
       Tally to answer the company check ... answered: true/false after N check(s)" and "the run stopped at the first
       request that did not answer". Nothing after the hang is measured in that run. If Tally does not come back
       within a few minutes, close and reopen it before the next run.
   Write down: for each of the four, the ms, bytes and count of its lines, and which (if any) says HANGS, with its
       fields.
   If not: send the report files and icon > Show log.

A2. THE MADE-UP BIG COMPANY (200,000 entries) - items a to d at scale
   Do, once, on a computer with Python 3:

   Write down: the same numbers as A1. Of interest most: b, c1, c2 and d at 200,000 entries.


PART B. WHAT MOVES THE ALTERID (snapshots)

For each test below:
   1. FinComBridge.exe measure --company "ZZ TEST" --snapshot b<N>-before      (N = the test's number)
   2. do the change in TallyPrime, exactly as written
   3. FinComBridge.exe measure --company "ZZ TEST" --snapshot b<N>-after
   4. FinComBridge.exe measure --compare b<N>-before b<N>-after
   5. write the comparison's lines into the table at the end
   Use an entry of the current month (snapshots cover one month; --month yyyymm for another month, the same in both).

B1. BANK RECONCILIATION: set the bank date of one payment in Banking > Bank Reconciliation; save.
B2. BILL SETTLEMENT: make a receipt against an existing sales bill (Agst Ref) of this month.
B3. DATE CHANGE: alter one entry and change only its date (stay in the same month).
B4. DELETE AND RE-ENTER: delete one entry (Alt+D), then enter it again by hand, the same in every field.
B5. ALTER WITHOUT CHANGE: open one entry, press Ctrl+A to save it without changing anything.
B6. A MASTER: rename one ledger used by an entry of this month (snapshots show whether the entries' AlterIDs move).
B7. RESTORE: back the company up (Data > Backup), make one entry, restore the backup over the company, then snapshot.
B8. REPAIR: Data > Repair the company, then snapshot.
B9. SPLIT: split a copy of the company at 1 April (Data > Split), open the new part, snapshot it (compare with the
    snapshot of the original).
B10. IMPORT: export one entry (Day Book > Export > XML), delete it, import the file back, snapshot.

The comparison prints: whether the company's GUID is the same, the highest AlterID before and after, and each entry
"changed" (AlterID, MasterID, date or number), "added" or "gone" (an entry deleted and entered again shows as one gone
and one added: a new GUID).
